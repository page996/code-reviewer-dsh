# 数据一致性与迁移

目标：数据层改动不得造成不可恢复的不一致、锁表或回滚失败。

## 必查点
1. 事务边界：多步写入是否在同一事务；事务内是否有网络/长耗时操作；N 次单条写入循环（应批量/批处理）。
2. 迁移安全：DDL 是否锁大表（Postgres 加列默认值、加索引不带 `CONCURRENTLY`、改类型、重写表）；是否可回滚/向前兼容。
3. 兼容顺序：先加列后写、先双写后切换、删列前先下线读；滚动发布期间新旧代码能否同时工作。
4. 约束与默认值：新列 NOT NULL 无默认值；缺唯一约束导致重复；外键级联删除范围是否过大。
5. 删除语义：物理删除 vs 软删除是否一致；漏改查询条件导致已删数据仍可见；级联缓存未失效。
6. 查询正确性：分页无稳定排序（结果重复/丢失）、`COUNT(*)` 大表、缺索引的高频过滤、N+1 查询。
7. 精度与时区：金额用浮点、时间存字符串/本地时区、`timestamp` 无时区语义导致的偏移。
8. 缓存一致性：缓存与数据库写入顺序、失效时机、并发回填（cache stampede）、缓存键缺少租户/版本维度。
9. 回填与批处理：大表全量 UPDATE 无分批；回填脚本非幂等，重跑产生重复数据。

## 证据要求
- 具体 SQL/迁移/数据访问代码位置（文件:行）与预计影响行数/表规模（能推断时给出）。
- 说明在滚动发布、失败重试、并发写入哪种场景下出错。
- 给出可回滚方案或正确顺序，指出当前顺序缺失的步骤。

## 判定
- blocker：数据丢失/不可逆迁移/生产锁表/唯一性被破坏。
- major：可恢复的不一致、性能显著退化、缓存脏读有明确触发条件。
- minor：仅测试/小数据量场景可复现。

> 软删除/墓碑高频问题：墓碑记录是否仍被计入配额、枚举、统计与树结构（batch-12 实测：删除永不物理清除，累计 120 个根后配额永久 409）；`schemaVersion` 只写不校验；配额/子节点计数用未过滤的 readdir（把 `*.tmp` 残留与墓碑算进去）。
